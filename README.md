## Що працює

- Додавання, редагування, архівування та видалення людей. ПІБ, позивний, звання, посада, підрозділ, телефон, група/екіпаж, дата початку служби, примітки. Перевірка дублікатів ПІБ та позивного.
- Єдина поденна форма подій. Календар у кожному полі дати та кнопка вибору дня. Кінцева дата включається. Перетини активних кадрових періодів однієї людини заборонені.
- Місячні кольорові графіки роботи та кадрових відсутностей. Повне ім’я кожного, позивний, підсумки днів та кількості людей за день. Клік по клітинці відкриває період або створення нового.
- Відпустка, КЗВ, лікарня, лікарняний, реабілітація, ВЛК. Повернення на ППД завершує лише вибрану відсутність і зберігає початкові планові дати.
- Картка людини: історія, планові періоди, дні роботи/відсутностей за вибраний місяць, дні від початку служби, давність відпустки/КЗВ. Понад 60 днів — червона позначка, 31–60 — жовта, до 30 — зелена. Немає історії — окрема нейтральна позначка.
- Довідники посад і груп. Перейменування оновлює картки; видалення групи не видаляє людей.
- Пошук, фільтри груп, типів подій, архіву. Порожній список має пояснення та скидання. Перехід у нову вкладку скидає попередні фільтри.
- XLSX/CSV-імпорт людей з попереднім переглядом і пропуском дублікатів. Перший аркуш, колонки за шаблоном експорту. XLSX-експорт списку людей та поденного табеля. Формули з імпорту не виконуються.
- Журнал: час, користувач, дія та старі/нові значення. Дата показується за Europe/Kyiv.
- Автоматична копія перед кожною зміною, останні 100 версій. Відновлення копії також спочатку зберігає поточну базу. JSON-експорт для окремого зберігання.
- Спільна база для кількох користувачів. Оптимістичне блокування: застаріла вкладка не може мовчки перезаписати новіші зміни.
- Адміністратор, редактор, лише перегляд. Одноразові запрошення діють 48 годин. Адміністратор може вимкнути доступ користувача. Паролі PBKDF2, токени зберігаються на сервері лише як хеші. Сеанс 8 годин.
- Адаптивний інтерфейс. Можна встановити сторінку як застосунок через меню браузера; офлайн-кешування персональних даних не використовується.

## Запуск на PC

Двічі натисніть `start.bat` або:

```powershell
python server.py --open
```

Відкрийте `http://127.0.0.1:8765`. Під час першого запуску консоль покаже логін `admin` та випадковий пароль. Збережіть його. Після входу пароль змінюється у налаштуваннях. Початкова база порожня, типове розташування — `%USERPROFILE%/PersonnelWeb/personnel.sqlite3`.

Для явного розташування бази:

```powershell
python server.py --database data/personnel.sqlite3 --open
```

Окрема вигадана демобаза:

```powershell
python demo.py
```

Адреса `http://127.0.0.1:8766`, логін `demo`, пароль `DemoOnlyPassword123!`. Ці облікові дані тільки для локального тесту. **Не використовуйте demo.py для сервера з реальними даними.**

## GitHub Pages та онлайн-база

### Безкоштовний варіант: GitHub Pages + Cloudflare Workers / D1

`cloudflare/worker.js` реалізує API з тими самими кадровими можливостями для Cloudflare Workers. `cloudflare/schema.sql` створює порожню D1-базу. Це альтернативний сервер: Python для PC, Worker для безкоштовного хостингу. Паролі у Worker хешуються WebCrypto PBKDF2-SHA256 із 100000 ітерацій (ліміт цього runtime); локальний Python використовує 300000. Паролі та токени двох серверів не переносяться автоматично.

1. Авторизуйте офіційний Wrangler із дозволами читання облікового запису, `workers_scripts:write`, `d1:write`.
2. Створіть D1 `personnel-workspace`, внесіть її ідентифікатор і свій `account_id` у `cloudflare/wrangler.jsonc`.
3. Застосуйте `cloudflare/schema.sql` один раз. Для подальших змін використовуйте окремі міграції, не очищайте базу.
4. Розгорніть Worker: `wrangler deploy --config cloudflare/wrangler.jsonc`.
5. Додайте секрет `ADMIN_PASSWORD` через `wrangler secret put ADMIN_PASSWORD --config cloudflare/wrangler.jsonc`. Його значення ніколи не записуйте в код. Перший правильний вхід із цим паролем створює адміністратора. Після створення адміністратора секрет можна видалити.
6. У `ALLOWED_ORIGINS` залиште точну адресу GitHub Pages. Адресу Worker додайте як repository variable `API_URL` і повторно запустіть Pages workflow.

У безкоштовних планів діють квоти Cloudflare. Тарифи та квоти перевіряйте в офіційній документації: https://developers.cloudflare.com/d1/platform/pricing/ . Платний план не потрібен для початкової невеликої бази; при вичерпанні квот запити можуть відхилятися. Доступ до бази перевіряється сервером для кожного запиту; GitHub містить лише код, а не кадрові записи.

Перевірки Worker: `node --test tests/worker.test.mjs` (Node 22.13+ із вбудованим SQLite). Тести використовують окрему базу в пам’яті, а не Cloudflare D1 користувача.

GitHub Pages розміщує статичний інтерфейс, але не запускає Python і SQLite. Крім рекомендованого безкоштовного Worker, доступні такі варіанти:

1. **Рекомендований простий варіант:** весь застосунок на HTTPS-сервері, який запускається з цього GitHub-репозиторію. Браузер і API працюють на одній адресі, база — на постійному диску.
2. **GitHub Pages + API:** інтерфейс на Pages, Python API на окремому HTTPS-сервері з постійним диском. Без API Pages показує лише вигадане демо для перегляду. Це не спільна онлайн-база.

### Сервер із GitHub через Render Blueprint

У репозиторії є `render.yaml` і `Dockerfile`. Створіть Blueprint із цього репозиторію в обліковому записі Render. У шаблоні використано постійний диск; це може вимагати платного тарифу. Актуальні умови перевіряйте перед створенням сервісу. Автоматично тариф не купується.

Задайте значення в панелі хостингу, не в GitHub-коді:

| Налаштування | Значення |
|---|---|
| `ADMIN_LOGIN` | Логін першого адміністратора |
| `ADMIN_PASSWORD` | Власний пароль від 12 символів; потрібен тільки для першого створення адміністратора |
| `DATABASE_PATH` | `/data/personnel.sqlite3` |
| `ALLOWED_ORIGINS` | Точна HTTPS-адреса фронтенду, без шляху та кінцевого `/`; кілька — через кому |
| `HOST` | `0.0.0.0` |
| `PORT` | `8765` або порт платформи |

Коли використовується лише адреса Render, додайте саме її в `ALLOWED_ORIGINS`. Після початкового запуску секрет `ADMIN_PASSWORD` можна видалити: обліковий запис уже є в базі. Зміна цього секрету не змінює існуючий пароль.

### GitHub Pages

1. У Settings → Pages виберіть GitHub Actions.
2. Якщо API вже розгорнуто, створіть Repository variable `API_URL` з його HTTPS-адресою, без кінцевого `/`.
3. Додайте `https://ВАШ-ЛОГІН.github.io` у `ALLOWED_ORIGINS` сервера.
4. Запустіть workflow **Publish frontend to GitHub Pages**.

Якщо `API_URL` не заданий, опублікується позначене вигадане демо з вимкненим збереженням. Після додавання `API_URL` перезапустіть workflow. Паролі, токени, файли SQLite та JSON-копії не завантажуйте в репозиторій.

HTTPS обов’язковий для інтернет-розміщення: TLS завершується на хостингу або reverse proxy, Python-процес слухає внутрішній порт. Сервер розрахований на невелику команду, один процес / один постійний диск. Копії всередині SQLite не захищають від втрати самого сервера: регулярно завантажуйте JSON у незалежне місце та налаштуйте резервування диска у хостингу.

## Перенесення з настільної програми

Перенесення не виконується автоматично. Локальний інструмент читає джерело лише для читання та експортує людей і кадрові відсутності. Не переносить робочі призначення, завдання, розташування та неструктуровані примітки.

```powershell
python migrate_personnel.py ../people.sqlite3 кадровий-експорт.json
```

Перевірте файл, потім у вебверсії **Резервні копії → Відновити з JSON**. Ця дія замінює дані вебверсії, тому потрібне підтвердження. Джерело не змінюється. Старі конфліктні або некоректні записи експортер відхиляє, а не виправляє мовчки.

## Windows EXE

### Авторизація, адмінка та автооновлення

У версії 2.1.0 є окрема вкладка **Адмінка**, видима лише адміністратору. Вона містить користувачів, запрошення, налаштування робочого простору та оновлення PC-програми. Авторизацію й права перевіряє сервер; приховування кнопок не є єдиним захистом.

Готовий EXE за замовчуванням відкриває інтерфейс і працює з **тією самою онлайн-базою та обліковими записами, що й сайт**. Дані не копіюються на PC: локальний сервер передає запити у фіксований захищений Cloudflare API. Для окремої локальної бази використовуйте `PersonnelWeb.exe --local`. З Python спільний режим запускається як `python server.py --online --open`. Посилання-запрошення з PC завжди ведуть на онлайн-сайт, а не на localhost.

Windows EXE автоматично перевіряє **GitHub Releases саме цього репозиторію**, завантажує нову стабільну версію та звіряє розмір, SHA-256 маніфесту і digest GitHub. Встановлення відбувається після закриття процесу, а не під час редагування. Старий файл зберігається як `.previous`; кадрова база лежить окремо та не замінюється. Увімкнути/вимкнути автооновлення, перевірити вручну або перезапустити для встановлення можна в адмінці локальної EXE-програми. Потрібен запис у папку з EXE; розміщуйте програму в доступній користувачу папці, не в Program Files.

Першу версію з автооновленням (2.1.0) потрібно встановити вручну. Старі EXE без модуля оновлення не можуть самі отримати цю можливість. У браузерного сайту інший механізм: нова версія надходить через GitHub Pages після оновлення сторінки.

Для наступного випуску оновіть `server.VERSION`, перевірте тести, створіть тег `vX.Y.Z` і відправте його в GitHub. Workflow **Publish Windows update** збере перевірений EXE та опублікує його з `update-manifest.json`. Без повного маніфесту автоматичне встановлення не працює. EXE перевіряється хешами, але не має платного сертифіката Windows Authenticode.

Workflow **Tests and Windows application** перевіряє код і створює артефакт `PersonnelWeb-Windows` із `PersonnelWeb.exe`. Завантажте його зі сторінки завершеного запуску Actions. Це збірка Python-сервера та інтерфейсу; код старої Tkinter-програми не включається.

Локальна збірка: `powershell -ExecutionPolicy Bypass -File build_windows.ps1`. Потрібен Python та інтернет для встановлення PyInstaller. Готовий файл — `dist/PersonnelWeb.exe`. Запуск з `--open` відкриває інтерфейс у браузері. Консоль залишена видимою, щоб перший пароль не загубився.

## Нові кадрові можливості 2.2.1

- **Адмінка → Створити користувача:** ручна реєстрація логіна з правами редактора або перегляду. Це окремо від особової картки людини. Самостійна реєстрація працює за одноразовим запрошенням; відкритої реєстрації до кадрової бази немає.
- **Групи та посади → Склад:** список усіх людей, пошук, додавання та вилучення позначками. Перенесення в групу не створює кадрових подій і не призначає роботу.
- **Новобранці:** категорії «Військовослужбовець», «Новобранець», «Стажер» в особовій картці та окремий список.
- **Адміністративні справи:** дошка загальних кадрових, документальних і господарських питань з пунктами, строком, текстовим відповідальним та станом.
- **Адмінжурнал:** ручні записи про документообіг, облік та господарські справи.
- **Заняття та оцінки:** загальні адміністративні курси, дата, викладач та ручні оцінки учасників 0–100. Бойова підготовка та автоматичне оцінювання придатності не реалізовані.
- **Excel:** оформлений кольоровий табель кадрових відсутностей, закріплені ПІБ і дати, формули підсумків, легенда, фільтр та альбомний друк. Порожні клітинки не вважаються вихідними: вони означають відсутність внесеного запису.
- **Повний резерв:** зашифрований AES-256-GCM файл з кадровими даними, користувачами (хеші паролів), журналом і кадровими резервними версіями. Тимчасові сеанси та одноразові запрошення не переносяться. Пароль файлу не передається серверу.
- Повне відновлення доступне лише адміністратору, потребує фрази «ВІДНОВИТИ БАЗУ» та копії від того самого типу сервера. Після відновлення потрібно ввійти повторно з обліковими даними з копії. Перед відновленням завантажується зашифрована копія поточного стану; сервер також зберігає страховий резерв. Для дуже великих копій, які перевищують квоти D1, використовуйте відновлення через адміністратора Cloudflare.
- `backup_windows.py` читає локальний DPAPI-зашифрований страховий резерв. Такий файл прив’язаний до Windows-облікового запису, з якого його створено; для перенесення на інший комп’ютер використовуйте парольний резерв із сайту.

Оновлення не очищає людей і не замінює робочу базу демоданими. Структурна міграція `cloudflare/migrations/0001_recovery.sql` лише додає таблицю страхових копій. Бойова робота, розвідка, бойові групові призначення та ротації не входять до функцій цього проєкту.
