# Зміни 2.4.0 — склади та робочі зміни

## Що додано

- «Склади»: створення, редагування, адреса/номер, поточні групи й працівники, наступні виходи, історія. Видалення означає архівування зі збереженням історії. Активні зміни блокують архівування.
- «Вихід на роботу» у групі та на складі: усі або вибрані працівники, відповідальний, час початку й завершення, примітка, сім статусів, фактичне завершення. Для нічної зміни вказується наступна дата завершення.
- «Зміни на складах»: день, тиждень, місяць, довільний період; календарна сітка тижня/місяця, групування за датами, складами, групами й працівниками; фільтри; повторення щодня, через день або щотижня до вибраної дати (до 366 днів).
- Перенесення дня, складу й учасників через «Відкрити». Завершені й скасовані зміни доступні для перегляду. Незавершену зміну можна скасувати.
- Excel з кольоровими статусами й закріпленими колонками; «PDF / друк» відкриває підготовлений альбомний документ — у системному діалозі вибрати «Зберегти як PDF».
- Знімки складу учасників і назви складу зберігаються в кожному призначенні. Історія доступна у групі та особовій картці, навіть після переведення чи видалення людини. Статистика враховує завершені зміни, а години у звіті за період обрізаються його межами.
- На обох серверах перевіряються перетини інтервалів працівника, включно з нічними змінами. Сусідні зміни без перетину дозволені. Фактичне завершення враховується замість планового. Автори призначень визначаються сервером, а не даними браузера.
- Фонове оновлення змін інших користувачів кожні 30 секунд у відкритій активній вкладці, коли немає відкритої форми. Контроль версії залишається обов'язковим при збереженні.
- Наявні незалежні «Адмінка», «Налаштування» та профіль збережено. Нові записи журналу змін і адміністративних дій містять ID виконавця. Історичні записи журналу не переписуються. Мова інтерфейсу — українська.

## Дані та міграція

Змінено лише код. Робоча локальна й онлайн-база під час розробки не відкривалися для запису. Перевірки використовують тимчасові бази та вигаданих людей.

Перед змінами створено окрему копію коду `ATB-before-changes-20261021` у робочій папці Codex. Це копія коду, а не підтверджений резерв робочої D1.

Міграція стану додавальна: нові поля `warehouses` і `shifts` мають порожні значення за замовчуванням. Нових SQL-таблиць для них немає; люди, групи, події та облікові записи не замінюються. Старі клієнти, які не передають ці поля, не стирають їх. Журнал і звичайні автоматичні копії також включають нові таблиці стану.

Перед оновленням робочого сервера адміністратору слід завантажити повний зашифрований резерв у розділі «Резервні копії». Цей крок не виконано за робочого користувача.

## Резервні копії

Cloudflare: щодня о 03:00 UTC, AES-256-GCM, перевірка розшифрування перед записом, останні 30 записів у D1. Потрібна раніше створена таблиця `scheduled_backups` з міграції `0003_daily_backups.sql` і секрет `BACKUP_KEY` — base64 від 32 випадкових байтів. Існуючий ключ не змінювати: він потрібен для старих копій. Ключ зберігати також незалежно від хостингу.

Незалежне зберігання вмикається конфігурацією, автоматично не підключається:

1. R2: створити приватне сховище й додати binding `BACKUP_BUCKET` у Wrangler. Налаштувати строк зберігання об'єктів у R2 відповідно до потреб; код не видаляє незалежні архіви. Для великого зашифрованого архіву D1 містить лише посилання, а файл — R2.
2. Приватний GitHub: задати `BACKUP_GITHUB_REPO=owner/private-repository` та секрет `BACKUP_GITHUB_TOKEN` з доступом Contents write лише до вибраного репозиторію. Код перевіряє, що репозиторій приватний, і надсилає лише шифротекст. Максимум цього експортера — 20 МБ на архів; для більших архівів використовувати R2. Історія Git зростає: це варіант для невеликих копій, не основна база. Очищення історії/строк зберігання — окрема операція адміністратора.

У розділі резервів показано, які зовнішні сховища налаштовані. Наявність binding або змінної не доводить успішне резервування: після налаштування виконати ручне створення й перевірити завантаження/відновлення. У разі відмови зовнішнього експорту мала копія залишається в D1, а операція повідомляє про помилку.

Зовнішній JSON-архів можна вибрати у формі повного відновлення на тому самому типі сервера з тим самим `BACKUP_KEY`; пароль у цій формі використовується для страхового резерву поточного стану. Для незалежного аварійного розшифрування є `decrypt-external-backup.mjs`: передати ключ через змінну середовища та два шляхи (вхід і новий вихідний файл). Розшифрований JSON містить персональні дані й не повинен потрапляти в Git. Відновлення великої копії обмежене можливостями D1 та потребує оператора хостингу.

Локальний Windows-сервер: автоматична повна DPAPI-копія під час запуску й потім раз на добу, доки сервер працює; останні 30 файлів у `daily-backups` поряд із базою. Ручне створення й завантаження через той самий розділ резервів. DPAPI-файли прив'язані до поточного Windows-користувача. Для перенесення використовувати парольний резерв з інтерфейсу. На інших ОС доступний ручний парольний резерв; щоденний файловий DPAPI-резерв там не підтримується.

## Хостинг і межі

За конфігурацією: інтерфейс і API — Cloudflare Worker `personnel-workspace-api`; постійна база — D1 `personnel-workspace`. Python/SQLite залишається локальним варіантом. Фактичний тариф, витрати, секрети та опублікована версія в кабінеті не перевірялися. Перезапуск Worker не є очищенням D1; перевищення квот може блокувати запити.

Перевірено за офіційними джерелами 21.10.2026:

- Workers Free: 100 000 запитів/добу, 10 мс CPU на HTTP-запит: https://developers.cloudflare.com/workers/platform/limits/
- D1 Free: 5 млн прочитаних рядків/добу, 100 000 записаних рядків/добу, 5 ГБ сумарного зберігання: https://developers.cloudflare.com/d1/platform/pricing/
- D1: до 2 000 000 байтів на рядок/BLOB; окремі ліміти на розмір бази й запити: https://developers.cloudflare.com/d1/platform/limits/
- GitHub блокує звичайні файли понад 100 MiB, рекомендує невеликі репозиторії: https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github

Поточна архітектура зберігає весь робочий стан одним JSON-рядком. Практичний обсяг даних обмежується цим рядком і лімітом API 2 МБ, а не лише квотою 5 ГБ. Для значного росту потрібна окрема міграція стану в нормалізовані таблиці; зовнішнє резервування саме по собі цього не змінює. Повний резерв може бути значно більшим за стан через журнал і 100 версій. Налаштування зовнішнього сховища не скасовує обмежень пам'яті/CPU Worker.

Перенесення на інший хостинг можливе: Python потребує постійного диска, D1 — експорту/імпорту SQL. Парольні хеші Python і Worker мають різну кількість ітерацій PBKDF2, тому пряме перенесення облікових записів між цими двома типами серверів потребує окремої міграції. Повне відновлення з інтерфейсу приймає резерв відповідного типу сервера.

## Перевірки та публікація

Пройшли 43 Python-тести, 19 JavaScript-тестів і браузерний сценарій на ізольованій D1-імітації: вхід, склад, призначення групи, календар, повторне завантаження, мобільний вигляд. Відмови при перетині, конфлікті версії, активному складі та правах viewer перевірені через API. R2 і GitHub перевірені імітованими зовнішніми сервісами. Реальні зовнішні сховища й виробниче розгортання цими тестами не перевіряються.

Команди: `python -m unittest discover -s tests`, `node --test tests/*.test.mjs`. Додатковий сценарій `node tests/ui-smoke.cjs` потребує Playwright і браузера; шляхи можна передати через `PLAYWRIGHT_MODULE` та `BROWSER_EXE`. Перевірка не використовує мережевий API або робочу базу.

Онлайн-публікацію та новий EXE-реліз під час цього допрацювання не виконано. Для Cloudflare використати наявний workflow/`wrangler deploy --config cloudflare/wrangler.jsonc` після повного резерву та налаштування потрібних секретів. Збірка EXE залишається через `build_windows.ps1` або наявні GitHub Actions.

Основні файли: `server.py`, `shifts.py`, `local_backups.py`, `fullbackup.py`, `web/app.js`, `web/shifts-model.js`, `web/shifts-ui.js`, `web/style.css`, `web/excel-styles.js`, `web/index.html`, `cloudflare/worker.js`, `cloudflare/backup.js`, `cloudflare/scheduled-backup.js`, `decrypt-external-backup.mjs`, `package.json`, тести й workflows. Повний перелік змін — у `upgrade-manifest.json`.
